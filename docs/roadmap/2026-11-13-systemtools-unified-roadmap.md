## 1. 项目怎么推进

根据用户最新决定，**所有后续跨平台改造统一在原版仓库 Programmer-MrWang/SystemTools 的 codex/cross-platform 分支推进**。以该分支上的 Windows 原版为基础逐步重组；原版 main 作为现有发布主线，当前独立跨平台仓库仅作为迁移参考与已验证修复来源，不再承担新的跨平台功能开发。

工作目录：/Library/root directory/My github project/SystemTools。参考目录：同级 ClassIsland 和 SystemTools-Cross-platform。发布身份继续沿用 SystemTools。分支建立在本轮读取的原版 HEAD 上，当前提交仅保存规划资料。

先完成三个可独立验收的里程碑，再扩展跨平台功能：

1. 三端各自从源码编译和加载；同一个试验包能在三端选择正确实现。
2. Windows 原有功能、ID 和旧配置经过逐项回归，确认没有因拆分丢失。
3. 用一项真实功能贯穿三端：发现能力、展示设置、执行、失败反馈和资源清理全部走通。

每项后续功能都复用这条路径。不要等所有功能完成才第一次打包、第一次在 Windows 或 Linux 上运行。

“代码可以重写”用于解除结构限制；不把全部业务逻辑同时重写当作目标。尤其在建立 Windows 基线前，不同时重做 UI、配置格式和语音实现。

## 3. 不轻易改变的约束

- Windows 以原版已交付功能为基线。修改内部组织不能成为裁剪功能的理由。
- Windows 普通退出无条件执行 shutdown /a 的行为按既有用户决策保留。
- 之前明确删除的网页时钟不自动恢复；若将来要求 Windows 原版严格零删除，应单独确认这一产品例外，不阻塞平台骨架。
- Linux 仅 X11；不实现 Wayland/XWayland。
- Mac 仅原生 osx-arm64，不要求 Rosetta，也不附带 Intel Mac 方案。
- 原版当前明确是 Windows x64。Linux 首个架构和受测发行版在阶段 0 记录，建议先 linux-x64；不得因为 C# 可编译就宣称所有 Linux 架构都支持。linux-arm64 作为另外的构建和原生依赖目标评估。
- 不以“另一个平台不支持”为理由删除配置、密钥、工作流或宿主认证项。
- 三端开发构建不要求其他平台的 SDK/专属运行环境；完整通用发行包由分平台构建结果汇总。
- 旧工作流中的不支持项需要可理解的诊断，不冒充执行成功。

## 5. 建议的工程结构

初期保持少量工程，不为每个按钮单独拆工程：

    SystemTools                     平台中立入口、公共界面、配置和功能注册协调
    SystemTools.Contracts           平台服务契约、结果模型、能力描述
    SystemTools.Platforms.Windows   Windows 行为与依赖，尽量沿用原实现
    SystemTools.Platforms.Linux     X11、D-Bus、设备与音频适配
    SystemTools.Platforms.MacOS     Apple Silicon 平台适配
    native/macos                   按需添加的原生桥接；确有需要才建立
    workers                        语音等需要隔离或独立运行时的工作进程
    tests                          通用回归、宿主契约、加载和平台集成验证
    eng                            本机构建、三端汇总打包、清单与依赖检查

主入口面向 net10.0，平台模块按需要使用平台目标或原生桥接。通用入口的公开类型、静态初始化、配置序列化和 XAML 不能要求加载 Windows 程序集。Windows-only 设置页和类型留在 Windows 模块；共享页通过平台中立模型和模板展示差异。

平台模块负责提供具体服务，并注册尚未抽取的原版专用行动。一个行动 ID 只允许一个实现生效，不能共享包装行动和旧 Windows 行动同时注册同一个 ID。

优先在输入、窗口、音频端点、设备、屏幕捕获、凭据等有真实差异的地方引入接口。纯算法、数据模型和普通文件处理直接共享。先完整迁入 Windows 专用模块，再逐步抽取公共流程，不要求第一天把原版每个类都改造成接口。

### 编译选平台，运行选实现

- 开发时：仓库统一构建入口只选择共享部分和本平台模块；其他平台项目、包、生成器和工作进程不参与本机默认 restore/build。
- 解决方案、项目引用和脚本都要检查。仅对 ProjectReference 加条件、却让默认解决方案仍直接构建全部平台工程，仍不符合要求。
- 本机普通编译不运行生成 CIPX 的 AfterBuild 目标，不依赖原版硬编码的 E 盘路径，也不自动同步 SAI 到真实宿主目录。
- 发行时：三台构建环境提供模块及平台资产，汇总出一个包；安装后入口按运行平台和进程架构选择模块。
- 所有共享程序集由统一依赖版本产生；不能把三份输出目录相互覆盖来“合包”，也不能简单拼接三份 deps.json。
- 根目录托管 DLL 与 native 子目录的布局必须适配宿主实际解析器；不假定托管后端放进任意 runtimes 子目录会自动被找到。

### 统一功能与能力判断

推荐用一个轻量功能目录统一描述：稳定 ID、设置类型、平台实现、可见入口、依赖条件及验证状态。各平台实现报告能力，不在页面、AI 和 SAI 中各写一套 OS 判断。

至少区分：

| 状态 | 新增行动/功能目录 | 设置与执行反馈 |
| --- | --- | --- |
| 可用 | 可以选择 | 正常执行并报告结果 |
| 可实现但未获权限 | 暂不作为可执行功能，或按明确授权流程激活 | 设置中提供授权入口，启动时不弹权限 |
| 需要可选依赖 | 依赖到位后开放 | 在扩展设置中说明安装与平台架构 |
| 无硬件/无后端/平台不支持 | 不出现在新建功能入口 | 保留已有配置，旧自动化显示原因 |
| 用户主动关闭 | 按原有启用开关处理 | 不擅自重新开启 |

能力探测避免产生副作用；授权请求只在用户明确启用或调用时发生。执行前再次检查动态能力，处理设备拔出、权限撤销和音频端点切换。

**旧配置的例外路径要单独设计。** 宿主当前在无法解析行动提供方时可能直接 return。隐藏入口不能等价于默默跳过旧行动；需要支持“不可新建但旧记录可显示错误”的兼容路径。可通过最小的缺失行动诊断适配解决；如果需宿主提供正式标记，应单列宿主改动，并在 AI/SAI 目录排除诊断占位项。不能只检查菜单是否隐藏。

## 6. 分阶段里程碑

### M0：冻结范围与兼容基线

目的：让“Windows 功能保持”有可核对的清单。

交付：

1. 记录三份源码、依赖版本、必要工作区状态与可恢复标签；使用已创建的 codex/cross-platform 分支推进；本轮没有开始实现改造。
2. 从实际注册和可见 UI 生成 Windows 功能台账：行动、触发器、组件、规则、主题、授权器、AI、导出、SAI、托盘和扩展依赖。
3. 为每项标记身份、设置字段、默认值、恢复/中断、可选依赖、权限、测试方式和平台目标。
4. 建立脱敏的旧 Main.json、自动化、组件布局、悬浮窗、会话与认证配置夹具；不提交真实密钥或人脸凭据。
5. 记录宿主版本、Windows/macOS 最低版本及 Linux 受测环境；以实际项目配置和运行结果为依据，不能仅凭目标框架名宣称最低系统支持。
6. 原版 Windows 冒烟测试记录：启动、全部设置页、既有工作流和扩展功能。涉及真实硬件的部分由对应机器记录，不用静态分析代替。

验收：每项现有 Windows 功能有台账和验收方法；恢复到基线的步骤明确。

### M1：构建与加载验证，越早越好

目的：证明架构能承载“本机构建 + 同一个包”，先不搬齐业务。

交付：

- 平台中立入口、最少的契约和三个平台模块；一个设置页和一项无副作用的宿主行动。
- Windows、Linux X11、Mac ARM64 分别 clean restore/build。
- CI 构建矩阵，先验证原生 ARM64 Mac runner 是否真实可用；不假定所有 macos runner 都是 ARM64。
- 早期汇总打包工具，生成含三端小型模块的同一个试验 CIPX。
- 三端用同一文件哈希的包通过真实宿主启动，记录入口、程序集来源和本机加载模块。
- 错误平台 DLL、缺少可选依赖、SAI 未安装的加载负向测试；Mac 不得尝试加载 WinForms、SAPI、Windows native DLL。
- 用独立测试宿主配置，不破坏正在使用的 ClassIsland 目录。

必须在此阶段处理的疑点：

1. 宿主在 Initialize 前枚举入口程序集公开类型，OS 判断不能修复过早的类型依赖。
2. 原版启用 WinForms，而插件不能假设能给宿主进程额外引入 Windows Desktop 共享框架；先验证宿主运行环境。必要时将消息窗口/键名辅助替换为行为等价的 Win32/Avalonia 实现，保持 Windows 功能不变。
3. Mac 托管程序集与 native 解析规则不同，不重复载入宿主 ClassIsland/Avalonia/WinRT，避免类型身份分裂。
4. Mac native 签名、目标架构、最低 OS 和宿主运行时的兼容性先做最小验证。

验收：三端本机编译和同包加载均有实际证据。只有某一端编译日志或强制模拟平台判断不算通过。没有对应机器时保持未验收，不开始宣称三端发行完成。

### M2：完整接入 Windows 原版，先保住主线

目的：架构调整后，Windows 用户得到完整原功能。

交付：

- 原有 Windows 行动、触发器、授权器、摄像头、人脸、SAPI/Vosk、设备控制、截图、玻璃、歌词和托盘逐组迁入 Windows 模块。
- 公共设置壳调用 Windows 模板；保留原有行为，不同时重做全部 UI。
- Windows 的可选 DLL、模型和 Worker 按原有扩展语义加载；改掉跨平台启动时全局预加载和非本机依赖初始化。
- 保留原版行动 ID、组件 GUID、主题 ID、通知渠道和认证提供方身份；核对 avares 资源 URI，移动程序集不能让旧主题资源失效。
- 导入现有缺陷修复时逐项对照，结构移动和行为修复分开提交。
- Windows 全功能台账逐项验证，包含 SAI 已装/未装、扩展已装/未装、授权成功/拒绝及卸载清理。

验收：Windows 功能台账无遗漏；旧配置可加载并工作；不能用原版功能被隐藏来让测试通过。暂时不支持的 Linux/Mac 功能继续隐藏。

这是最重要的保真验收点。到达后，哪怕后面的 Mac/Linux 扩展暂停，项目也已有完整 Windows 功能，而不是只剩一个重新搭建的壳。

### M3：共享能力、配置和历史数据收敛

目的：将真正公共的能力合并，而不是把两个版本长期拼在一起。

交付：

- 合并文件操作、通知、规则、课程/档案行动、基础组件、主题、悬浮窗布局、AI 会话/工具、Excel 与 SAI 的通用部分。
- 移植现有目录安全、快照恢复、稳定工作流身份、异步命令和中断检查；按统一项目组织重绑测试。
- 统一功能目录、生命周期和一次性清理；不重复创建麦克风、相机、通知提供方或轮询器。
- 处理正式版身份和旧跨平台身份迁移，见第 7 节。
- 设置跨平台未知字段的保留策略，避免 Linux/Mac 保存一次就丢失 Windows 扩展字段。
- 将 Windows DPAPI 保持在 Windows 后端；Mac Keychain、Linux Secret Service 等分别实现，无法读取旧密文时保留原值并提示重新配置。
- 认证能力在另一平台不可用时不移除宿主认证项，也不自动降级为更弱认证方式。

验收：迁移可重复执行而不重复创建对象，失败可恢复；Windows 原配置及跨平台旧配置都有脱敏夹具覆盖；AI/SAI/菜单/设置使用一致的可用能力清单。

### M4：Linux 与 Mac 基础功能，逐个完成三端闭环

先选择“系统音量”或“空闲检测”做完整示范；不只实现一个 native 方法就算完成。

每项包含：平台探测 → 设置/权限入口 → 新建行动 → 执行/中断/恢复 → 错误反馈 → 资源释放 → 原有 Windows 行为对照。

建议按下列小批次推进：

| 批次 | Linux X11 | Mac ARM64 | 共用部分 |
| --- | --- | --- | --- |
| M4.1 | PulseAudio/PipeWire 音量或 X11 空闲 | Core Audio 音量或 Quartz 空闲 | 能力、结果、轮询/设备变化与测试 |
| M4.2 | X11 截图、libudev/UDisks | ScreenCaptureKit、IOKit/挂载通知 | 文件输出、设备去重、自动打开 |
| M4.3 | XGrabKey、XTEST、EWMH | 热键/Quartz、Accessibility | 键盘模型、窗口语义与设置 |
| M4.4 | 桌面环境壁纸后端 | NSWorkspace 壁纸 | 图片取色、ClassIsland 主题和悬浮窗交互 |

Mac 权限声明与宿主补丁不能拖到功能完成后再做。采集和自动化相关声明、TCC 授权、签名和主线程要求在相应功能开始前验证。

验收：各项在支持与不支持环境都表现正确。Mac 普通层级不称为置底，Unicode 输入不机械复用 Windows VK，系统主音量不借用应用播放器音量。

### M5：语音、摄像头、认证与媒体

目的：在基础平台链路稳定后处理依赖重、状态复杂的功能。

建议内部再拆四批：

1. 摄像头单次抓拍，先验证授权、设备占用、输出和退出清理。
2. 语音听写，再做关键词/唤醒，最后做全双工对话与打断；不同功能共用录音所有权管理。
3. Windows Hello 保留，Mac 使用系统认证；Linux 暂不为统一菜单强做泛化生物认证。
4. 媒体播放规则先 Windows/Linux，歌词按真实来源做后端；Mac 通用媒体状态没有稳定已验证后端时不显示该项。

Windows SAPI/现有 Worker 可保留，Mac/Linux 使用各自 native 采音与识别后端。M 系列可验证 Vosk、whisper.cpp/Metal/Core ML 或 Apple Speech，但必须单独核对 C# 绑定、语言、离线能力和模型分发。现有 win-x64 Worker 不能复制后改文件名就当成跨平台。

验收：原生依赖只加载当前架构；拒绝权限不会导致整个插件失败；设备拔出、取消、重复进入、麦克风争用和宿主退出都有检查。保留 AI 行动/档案修改的已有本地审批。

### M6：复杂外观、背景捕获和硬件功能

目的：将风险集中在明确的子项目中，不拖住统一版本的基础交付。

- 主界面背后亮度：先验证排除自身后的真实画面，再复用明暗决策。
- OCR 避让：在捕获可用后处理识别、阈值、防抖与恢复，Mac 可验证 Vision。
- 玻璃：Windows 先保留原效果；Mac 原生玻璃/材质先做与 Avalonia 的叠层和命中原型；Linux 按合成器能力提供。
- 显示器：镜像/扩展与仅某屏分别验证，硬件外屏数量上限不作突破承诺。
- 亮度：内置背光、外屏 DDC 和软件变暗分别建模；无法验证的 Mac 后端保持不可用。
- Windows 设备启停、管理员重启等可长期是 Windows 独有，保留原功能不意味着其他端必须模拟出同名行为。

验收：每个子能力有明确支持环境和退路，不用“不报异常”代替实际生效。M6 不必全部完成才发布一个能力范围诚实的跨平台版本。

### M7：统一发行与旧版本退场

交付：

- 同一版本、同一提交来源的三端构建结果合包；清单记录平台、架构、依赖和版本。
- 对照包内容检查托管 DLL 重名/版本冲突，包含 native、资源、Worker 和必要的加载信息。
- 在三端分别安装同一哈希 CIPX，验证新装、旧版升级、重启、停用和异常恢复。
- 正式身份切换，旧跨平台包迁移后停用；不让两个同 ID/同 GUID 的实现同时注册。
- 可选大模型和依赖保留按平台安装的机制。一个 CIPX 不等于必须把所有识别模型都内置，但核心模块必须自洽，不要求用户自行寻找 DLL。
- 基础 CI 不因模型未下载而无法编译；扩展的编译、依赖校验和运行验收单独列任务。
- 文档从同一个能力目录/台账生成平台功能表，防止页面展示与运行能力脱节。

验收：同包、三端、旧配置、可选依赖与功能台账均有证据；原版维护分支保留作为回退，待稳定后再停止双线功能开发。

## 7. 身份、迁移与回退

### 正式身份

推荐正式统一版本继续使用 SystemTools 身份及原版稳定功能 ID，让原版 Windows 用户获得正常升级路径。仓库名、项目目录名、程序集拆分方式不必等于插件市场身份；避免把这些一起强制改名。

开发阶段使用独立的测试宿主数据目录和受控插件列表。即使更换测试 plugin ID，只要行动 ID/组件 GUID 与原版相同，就不能安全同时加载；预览包需要明确阻止冲突实例，不靠用户猜测。

### 旧跨平台用户

旧跨平台版使用不同插件 ID、行动前缀和组件 GUID，不能仅复制 Main.json。迁移范围至少包括：

- 主配置、启用字典、方案名称；
- 自动化、行动时间点、触发器和规则；
- 宿主组件配置、主题选择和悬浮窗按钮关联；
- AI 会话、附件引用和密钥状态；
- 通知配置与授权项中确需转换的身份。

使用明确 ID 映射和结构化遍历，不对整个 JSON 文本做前缀替换。原版与跨平台版各有配置时先预览冲突，不自动覆盖。为冲突提供“保留原版”“从跨平台版导入”“选择性导入”的产品流程，实际采用前再与用户确定。

迁移先备份、生成候选、验证、再提交；记录版本使其可重复执行。平台密钥不保证跨 OS 解密；不要因为密钥不可用而擦除原密文。

### 回退不能只靠 Git

Git 回退恢复代码，数据回退还需要旧配置与宿主相关配置备份。新版本写出的字段可能不能被旧版本保留，因此正式升级保留迁移前快照，并验证从新版本回退到指定旧版本的步骤。避免首次启动就不可逆覆盖旧配置。

## 8. 宿主需要配合的最小清单

| 宿主事项 | 为什么影响路线图 | 阶段 |
| --- | --- | --- |
| Mac 摄像头、麦克风与所用语音/自动化说明和授权 | 当前 bundle 未声明的能力不能由插件包自行补齐 | M1 调查，相关 M4/M5 前交付 |
| 稳定的可用能力/不可新建兼容项表达 | 旧行动不应被静默跳过，AI/SAI 也不能暴露不可执行项 | M3 前确定 |
| Mac 鼠标位置和窗口层级实际能力 | 当前 GetMousePos 为占位，Bottommost 未实现 | 对应 M4 功能前确认 |
| 稳定的设置持久化入口 | 运行时主题变更要与宿主设置、重启后的状态一致 | M3/M4 |
| 插件加载与依赖解析 | 多程序集及资源、native 桥接按真实规则布局 | M1 |

这是待验证的宿主协作清单，不等于每项都必须改宿主 API。先复用已有服务；确需宿主改动时，以独立小补丁和兼容设计提交，不把宿主重写纳入插件改造。最低宿主版本由实际所需接口与打包声明确定。

## 9. 每批如何审查与提交

建议的工作循环：

1. 选择一条台账记录和写入范围，说明 Windows 行为及要保持的契约。
2. 先读原版、宿主和现有测试；定义本批能验证什么。
3. 小范围修改；移动代码、改行为、迁移数据和改宿主分别提交。
4. 编译共享部分与本平台实现；检查没有隐含依赖另一平台 SDK。
5. 运行相关回归/契约检查；原生功能在对应系统验证，不用其他系统编译代替。
6. 审查 diff、配置变更、资源 URI、依赖产物和停止清理；再提交。
7. 更新台账与阶段记录，明确尚未验证项和回退方法。

推荐中文约定式提交示例：

- docs: 固化 Windows 功能与兼容基线
- build: 按当前平台选择插件项目与依赖
- refactor(windows): 隔离热键与系统消息窗口实现
- fix(config): 保留非当前平台的扩展配置
- feat(linux): 接入 X11 空闲检测
- feat(macos): 接入系统音量与设备能力探测
- test(host): 验证旧行动不可用时的诊断
- build(package): 汇总三端模块为同一插件包

每项功能的完成条件：支持端能执行，非支持端不提供新建入口，旧配置保留并有诊断，中断/恢复/退出正确，Windows 无未经说明的变化，测试与文档反映实际结果。

## 10. 验收矩阵

| 验收 | 自动化能做什么 | 还需什么实际环境 |
| --- | --- | --- |
| 三端源码构建 | 干净 restore/build、依赖和项目图检查 | 对应系统及 SDK；Mac 原生桥接需匹配工具链 |
| 同包加载 | 扫描/解析、错误平台 DLL 不加载、版本/资源检查 | 三端真实宿主安装相同包 |
| Windows 保真 | ID/设置快照、通用逻辑、生命周期 | Windows UI、权限、设备和原生功能 |
| Linux | 通用逻辑、X11 虚拟显示下部分窗口/输入 | 真实 X11 桌面、音频、USB、多屏与驱动 |
| Mac | ARM64 依赖检查、模型/契约、部分 UI | M 系列设备上的 TCC、原生窗口、Touch ID/相机等 |
| 迁移/回退 | 脱敏配置夹具、幂等、未知字段、失败恢复 | 干净安装与真实旧版本升级流程 |
| 重依赖功能 | 依赖版本、架构、负向加载与替身测试 | 模型下载后的录音、识别、设备占用和清理 |

现有工作区环境是 Mac ARM64。远程 CI 可作为未来构建手段，但本轮没有检查或授权使用具体 runner；没有 Windows/Linux 真实运行证据时必须明确标注缺口，不能在路线图里直接勾选验收。

## 11. 最容易让计划失控的做法

- 全面替换现有目录后再开始验证 Windows 功能。
- 只有运行时 OS 判断，却没有隔离项目和依赖。
- 在主入口/共享设置的静态初始化中预加载 Dlib、WinForms、SAPI 或 WinRT。
- 因 Mac/Linux 缺少 Windows Hello 而清除原认证配置。
- 用软件变暗代替硬件背光、用音频有声代替媒体播放、用指针事件代替鼠标穿透监听。
- 同一个 ID 注册两套提供方，或把每个缺陷都用“保留旧版本”无限期绕过。
- 只测某个平台的样例行动，而忽略公共设置页、序列化和未知配置也可能引用其他 OS 类型。
- 构建脚本在普通 build 中复制到用户宿主目录、清理现有 CIPX 或下载所有模型。
- 在打包时混入不同宿主版本的 ClassIsland/Avalonia，或依赖本机 NuGet 缓存掩盖漏包。

## 12. 建议第一轮实施的明确边界

第一轮只做 M0 + M1，交付“功能基线、构建骨架、三个最小模块、早期同包验证及结果记录”。

保留原 Windows 插件作为对照，不在这一轮同时完成 Windows 全功能搬迁、45 项能力扩展、UI 改版和正式迁移。通过加载/构建验收后，第二轮进入 M2；若没有可用 Windows/Linux 运行环境，明确列出所缺证据并先补环境。

宏观依赖：

    M0 基线
      → M1 三端编译与同包加载
      → M2 Windows 全功能保真
      → M3 共享能力与配置兼容
      → M4 Linux/Mac 基础功能
      → M5 语音、摄像头、认证与媒体
      → M6 复杂外观与硬件能力

M7 的打包工具从 M1 开始建设；第一个范围明确的统一版本可在 M4 验收后进入 M7，M5/M6 作为后续版本逐步增加。保留 Windows 完整功能不要求 Linux/Mac 在首次发行时就达到同样数量。

不在缺少原型与运行环境时给出“几天完成全部”的承诺。用上述验收点决定进度，遇到单个能力没有可靠后端时隐藏该能力，继续完成其他已确认功能。
