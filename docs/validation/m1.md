M1 是加载预览。新入口沿用正式 `SystemTools` 身份，但只提供一个诊断页和一个无系统操作的行动。原来的完整 Windows 代码仍在根目录项目，M2 再接入新架构。不要用此包升级日常插件，也不要把三端描述模块理解为所有功能已经跨平台实现。

Linux 只接受 x64 原生 X11；macOS 只接受 Apple Silicon 原生 ARM64；Windows 首个目标为 x64。Wayland、XWayland、Linux ARM64、Intel Mac/Rosetta 均不属于本轮支持目标。构建可以在 Linux 无图形会话中进行，运行验收必须是原生 X11。

## 工程与命令入口

- `SystemTools.slnx` 默认只列出新入口；入口按本机 OS 条件引用一个后端。直接 `dotnet build -c Release` 或指定此解决方案都已在 Mac 验证。
- `src/SystemTools`：中立入口、诊断设置页、诊断行动和试验包清单。
- `src/SystemTools.Contracts`：平台选择、进程架构/会话条件与最小接口。
- `src/SystemTools.Platforms.*`：三个独立的纯托管 M1 模块。
- 根目录 `SystemTools.csproj`：原 Windows 项目；目前仅排除新目录，保留生产逻辑，旧 Windows CI 明确构建这个项目。
- `eng/m1.py`：本机构建、试验合包、三端原生合包和隔离宿主测试。
- `eng/check_reproducible.py`：在相同提交/远程来源、两个路径重建并比较本平台七个输出。要求先提交构建输入。

开发依赖为 Git、.NET 10 SDK、Python 3.9+。M1 平台模块目标均为 net10.0；构建插件不需要其他 OS 的 SDK、Windows Desktop、Mac workload、OpenCV、人脸模型、Vosk、FFmpeg 或 SAI。CI 固定 .NET SDK 10.0.403，手动合包建议三台机器使用相同 SDK。

`python3 eng/m1.py build --clean` 先 clean、再 restore/build，严格按白名单把本机文件放入 `artifacts/m1/<rid>`；不自动创建 CIPX、不写真实宿主目录、不同步 SAI。构建输出可能包含 SDK 中间文件，打包不直接复制整个 bin。

## Windows 验证

使用 Windows 11 x64 测试机，安装 .NET 10 x64 SDK 和 Python。准备与本轮 API 契约相符的 ClassIsland 桌面宿主；关闭已运行的 ClassIsland，宿主使用全局单实例锁。下面所有命令在本分支仓库根目录执行。

```powershell
git switch codex/cross-platform
dotnet --info
py -3 eng/m1.py build --clean
py -3 eng/m1.py test
py -3 eng/test_m1_packaging.py
```

预期：本机构建只有 `SystemTools`、`SystemTools.Contracts`、`SystemTools.Platforms.Windows`；检查程序结尾为 `PASS: 19 M1 boundary checks; native runtime under test: win-x64`。这些测试加载的是随仓库冻结的真实宿主解析器，不等于桌面宿主启动测试。

将本轮 Mac 生成的 **同一个** CIPX 及 `.sha256` 复制到 Windows。当前已有真实 Mac 证据的文件名为 `SystemTools.M1.MacVerified.cipx`；下例可用该文件替换。不要在 Windows 重新打包后拿不同文件宣称同包验证。最新默认输出与已验证归档的区别见本文末尾。

```powershell
Get-FileHash 'C:\M1\SystemTools.M1.cipx' -Algorithm SHA256
py -3 eng/m1.py smoke --host-bin 'C:\ClassIsland\ClassIsland.Desktop.exe' --package 'C:\M1\SystemTools.M1.cipx'
py -3 eng/m1.py smoke --host-bin 'C:\ClassIsland\ClassIsland.Desktop.exe' --package 'C:\M1\SystemTools.M1.cipx' --case foreign-corrupt
py -3 eng/m1.py smoke --host-bin 'C:\ClassIsland\ClassIsland.Desktop.exe' --package 'C:\M1\SystemTools.M1.cipx' --case missing-backend
```

把宿主路径换成实际桌面可执行文件，有的发行包命名为 `ClassIsland.exe`。应直接使用桌面宿主，而非可能重写数据根目录的外层启动器。预期三项命令都返回 `PASS host smoke`；最后一项通过表示正确检测到本机后端缺失，不表示插件成功加载。

## Linux 验证

首轮建议 Ubuntu 24.04 x64，登录原生 Xorg/X11 桌面，准备可正常启动的 ClassIsland Linux 桌面宿主，以及 .NET 10 SDK、Python 3。先关闭已运行的 ClassIsland。

```sh
uname -m
printf '%s\n' "$XDG_SESSION_TYPE" "$DISPLAY" "$WAYLAND_DISPLAY"
python3 eng/m1.py build --clean
python3 eng/m1.py test
python3 eng/test_m1_packaging.py
```

应为 x86_64、会话类型 x11、DISPLAY 非空、WAYLAND_DISPLAY 为空。不要在 Wayland 中修改变量假装 X11。纯 X11 会话未导出会话类型时应先核对登录管理器/会话配置，再排查变量。此预览有意拒绝无法确定的会话。

预期本机构建只包括入口、契约和 Linux 模块；边界检查结尾为 `native runtime under test: linux-x64`。然后验证从 Mac 复制来的同一 CIPX：

```sh
sha256sum /path/to/SystemTools.M1.cipx
python3 eng/m1.py smoke --host-bin /path/to/ClassIsland.Desktop --package /path/to/SystemTools.M1.cipx
python3 eng/m1.py smoke --host-bin /path/to/ClassIsland.Desktop --package /path/to/SystemTools.M1.cipx --case foreign-corrupt
python3 eng/m1.py smoke --host-bin /path/to/ClassIsland.Desktop --package /path/to/SystemTools.M1.cipx --case missing-backend
```

使用桌面宿主的直接可执行文件；AppImage 可先按发行包说明提取出其桌面二进制。测试不负责补齐宿主自身缺失的 Linux 桌面库。若宿主不能独立启动，应先修复宿主运行环境，不把没有证据的启动计为通过。

## Mac 重现本轮检查

```sh
uname -m  # 必须 arm64
python3 eng/m1.py build --clean
python3 eng/m1.py test
python3 eng/test_m1_packaging.py
python3 eng/check_reproducible.py
python3 eng/m1.py prototype
python3 eng/m1.py smoke --host-bin '/path/to/ClassIsland.Desktop.app/Contents/MacOS/ClassIsland.Desktop' --package artifacts/m1/SystemTools.M1.cipx
python3 eng/m1.py smoke --host-bin '/path/to/ClassIsland.Desktop.app/Contents/MacOS/ClassIsland.Desktop' --package artifacts/m1/SystemTools.M1.cipx --case foreign-corrupt
python3 eng/m1.py smoke --host-bin '/path/to/ClassIsland.Desktop.app/Contents/MacOS/ClassIsland.Desktop' --package artifacts/m1/SystemTools.M1.cipx --case missing-backend
```

`prototype` 额外编译另外两个纯托管描述模块，因此会触及它们的项目；这是显式的试验合包步骤，不是默认开发构建。包内来源标记为 `local-managed-prototype`；不能把这些 Mac 上产生的 IL 程序集当作 Windows/Linux 原生构建验收。此模式只适用于 M1 尚无原生依赖的模块，后续 native 功能加入后必须改用原生构建资产汇总。

## 测试证据与手动界面检查

每次 smoke 创建全新的 `artifacts/m1/runs/<时间>-<场景>/sandbox`，写 `PackageType=folder`，通过宿主支持的 `ClassIsland_PackageRoot` 隔离日常插件、设置、档案和日志。宿主的机器级 `GlobalStorageService` 例外：它固定访问用户 LocalApplicationData 下的 ClassIsland/Global/Global.json，不受此变量控制。脚本只记录该文件运行前后哈希；变化即失败，不擅自覆盖恢复共享文件。早期三次成功证据尚未加入此全局存储观测，不能据此声称它已经验证。正常场景把原 CIPX 放进宿主的 `data/Cache/PluginPackages`，由真实宿主安装；负向场景从同包提取，再仅修改测试副本的后端 DLL。

脚本预置人工 Settings.json 跳过首次向导。源码核对发现 `--skip-oobe` 本身不能保证不阻塞 AppStarted，故不依赖该参数伪造“启动完成”。

- `host.log`：完整宿主 stdout/stderr。
- `result.json`：场景、运行平台、宿主可执行文件和 CIPX SHA-256、源内容哈希、旧夹具保留结果。
- `sandbox/data/Config/Plugins/SystemTools/M1.HostSmoke.json`：设置页通过真实宿主 keyed DI 取得；诊断行动经宿主 ActionBase.InvokeAsync 执行并完成；插件上下文只有一个本机后端。
- 缺本机模块时为 `M1.LoadFailure.json`，保留明确 FileNotFoundException。

三次场景中的 `packageSha256` 必须相同；三台机器最终也必须相同。正常/异平台损坏场景需 `passed=true`、正确 runtimeId、`IsCompleted=true`。夹具包括带 Windows 密文前缀的合成值和认证记录；宿主进程退出后 `fixtureHashesUnchanged=true`。这里只证明 M1 不动旧数据，不等于旧数据迁移已实现。

自动化测试会关闭它自己启动的宿主进程；不查找/终止其他进程。Windows 的 terminate 不是菜单普通退出，故不能用该脚本验收原 Windows `shutdown /a` 逻辑。正常退出/恢复/硬件行为留在 M0/M2 对应实机台账。

目视检查可在 GUI 可用的机器上，将结果目录里的 sandbox 路径作为 `ClassIsland_PackageRoot` 再启动同一宿主，打开设置中的「SystemTools M1 诊断」，点击「记录平台诊断」。应展示本机平台并提示保存成功，M1.Diagnostics.json 中 source 为 `settings-button`。再在自动化新建「记录平台诊断（M1）」行动并运行，source 应变为 `host-action`。不出现尚未移植的系统功能入口。

本轮 Mac 自动检查已验证页面构造和行动执行。完整设置窗口目视验证未计为已通过：另一次手动窗口启动及最终包复跑在插件初始化前遇到宿主 Avalonia.Native RenderTimer 错误 -6661。随后用 CoreGraphics 查询到主显示器 active=0、asleep=1；临时显示活动断言仍未恢复图形环境，已停止该断言进程。最后复跑保持失败记录，没有用旧结果覆盖。完整日志在各失败 run 的 host.log 和本机 `/tmp/systemtools-m1-ui.log`。需要显示器在线后重跑最终包；不要把这一限制误标为最终包通过。宿主自身的 ReactiveUI 可选程序集探测/渲染警告也不等同于插件上下文加载了 Windows 依赖。

本轮使用现有 Mac Debug.app，未重建宿主；源码契约/加载器快照来自 `3afce2714b6ec50d4bd2a3baac95a71d96ce3b9b`，运行二进制以 result.json 中路径和哈希为准，不能仅凭工作区 HEAD 推断二进制恰好来自该提交。

## 三端原生结果汇总与 CI

三台机器检出同一提交、同一源码内容、使用同一 SDK，各执行 build，汇集 `artifacts/m1/win-x64`、`linux-x64`、`osx-arm64` 三份目录后：

```sh
python3 eng/m1.py package --input /inputs/win-x64 /inputs/linux-x64 /inputs/osx-arm64
```

工具校验三端齐全、提交/源内容一致、每个文件哈希和公共文件字节一致。任何同名公共 DLL 或 deps.json 冲突均拒绝合包。入口 deps.json 只描述中立入口与契约；后端从插件根目录显式加载，不拼接三份 deps.json，不附带 ClassIsland/Avalonia/WinRT/Microsoft.Extensions 的第二份运行时。

`.github/workflows/m1-cross-platform.yml` 提供三端矩阵、Linux Xvfb 的 X11 解析器检查和汇总打包；不包含真实桌面宿主验收。Mac runner 当前选 `macos-15` 并在开始时检查实际 ARM64。官方 runner 表已于本轮核对，标签可能变化，实际架构断言必须保留。官方表：https://docs.github.com/en/actions/reference/runners/github-hosted-runners 。CI 尚未远端执行，其可用性与跨 OS 哈希一致性保持待验收。

本轮确实发现并修复了一个合包前置问题：手动 PathMap 只改编译文档路径，SourceLink JSON 仍带开发机绝对路径，嵌入 PDB 后使 DLL 不一致。现在启用 ContinuousIntegrationBuild/DeterministicSourcePaths，同时保留原 .gitattributes 的通用规则并固定共享源码 LF，Mac 跨路径重建已通过。三端真正汇总时仍必须让严格校验给出结果。
